# API compatible con S3

> **Experimental.** Verificada contra **boto3 real** (14 comprobaciones, incluidas
> URLs presignadas que caducan, multipart subido fuera de orden y los ETag) y con
> los vectores de prueba publicados de AWS para SigV4. No se ha ejecutado contra
> la suite mint de MinIO — ver *Qué no se ha probado*, abajo.

Los objetos viven donde el API de blobs nativo los guarda
(`{data_dir}/blobs/{bucket}/{key}`), así que los mismos bytes se alcanzan por
cualquiera de las dos puertas, el registro de propiedad aplica a las dos, y la
cuota de una organización los cuenta una vez. Dos almacenes habrían significado
dos cuotas, dos rutas de respaldo y dos formas de quedar inconsistentes.

## Arrancarla

```toml
s3_port = 9000    # 0 (por defecto) la deja apagada
```

Puerto propio porque S3 se adueña de la raíz del espacio de rutas: `GET /` es
ListBuckets y `GET /{bucket}/{key}` es cualquier objeto. Compartiendo router con
`/v1/...`, uno taparía al otro — `/v1/health` es un bucket perfectamente válido
llamado `v1` con una clave `health`.

## Credenciales

```bash
# Como admin de una organización:
curl -X POST localhost:1234/v1/admin/s3-credentials -H "Authorization: Bearer $KEY"

# Como admin de plataforma hay que nombrar la organización:
curl -X POST localhost:1234/v1/admin/s3-credentials \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"org_id":"acme"}'
```

El secreto se devuelve **una vez** y no hay endpoint que lo vuelva a mostrar.

> **Las credenciales S3 no son las api keys, y su radio de impacto es distinto.**
> SigV4 no envía una credencial: envía una firma derivada de ella, así que el
> servidor tiene que poder **derivar la misma clave** — y para eso necesita el
> secreto en forma recuperable. Las api keys se guardan como hash SHA-256 y aquí
> serían inservibles. El secreto S3 se guarda **cifrado** con `LUMA_MASTER_KEY`,
> no hasheado: un hash no lo revierte nadie, un secreto cifrado lo lee quien
> tenga la master key. Es inherente a SigV4, no un atajo. Rótalas en consecuencia.

## Clientes

```python
import boto3
from botocore.config import Config

s3 = boto3.client(
    "s3",
    endpoint_url="http://luma:9000",
    aws_access_key_id=ACCESS_KEY,
    aws_secret_access_key=SECRET_KEY,
    region_name="us-east-1",
    config=Config(
        signature_version="s3v4",              # obligatorio, ver abajo
        s3={"addressing_style": "path"},       # no hay DNS para bucket.host
    ),
)
```

Los dos parámetros de `Config` no son opcionales:

- **`signature_version="s3v4"`.** boto3 todavía presigna con **SigV2** por
  defecto, y Luma solo soporta SigV4. Sin esto, `generate_presigned_url` produce
  una URL que se rechaza. El servidor detecta esa forma concreta y lo dice en el
  mensaje, en vez de un «se requiere una petición firmada» genérico que mandaría
  a revisar las credenciales, que están bien.
- **`addressing_style="path"`.** El estilo virtual-host mete el bucket en la
  cabecera `Host`, y sin DNS comodín eso no resuelve.

## Qué está soportado

| | |
|---|---|
| Buckets | ListBuckets, CreateBucket, DeleteBucket (rechaza si no está vacío) |
| Objetos | PutObject, GetObject, HeadObject, DeleteObject |
| Listado | ListObjectsV2 con `prefix`, `delimiter`, `max-keys` y continuación |
| Multipart | Create, UploadPart, Complete, Abort |
| Firma | SigV4 por cabecera y por query (presignado, con caducidad) |
| ETag | MD5 del cuerpo para una subida simple; para multipart, MD5 de los digests de las partes más `-N`, como S3 |

## Qué **no** está soportado

Rechazado con el `NotImplemented` de S3, no ignorado en silencio: versionado,
lifecycle, ACLs, replicación, object lock, cifrado en servidor por cabecera,
tagging, configuración CORS y hosting web.

La distinción importa. Un cliente que pone una ACL y recibe un 200 **cree que el
objeto es privado** cuando no lo es; un 501 le dice la verdad.

## Divergencias conocidas

> **El ETag ya es MD5.** Era una divergencia declarada y está cerrada. El
> razonamiento original —no añadir una dependencia de un hash roto para un
> checksum— no se sostenía: `md-5` ya estaba en el árbol de dependencias, así que
> no costaba nada, y aquí MD5 no es una primitiva de seguridad sino un formato de
> cable. Un cliente que recalcula el ETag está buscando corrupción, y o coincide
> o la descarga parece corrupta.

| | |
|---|---|
| **Cuerpos chunked sin verificar** | `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` se acepta en la firma pero las firmas por chunk no se comprueban: la petición queda autenticada, el cuerpo no |
| **Sin acceso anónimo** | S3 lo permite para buckets públicos. En un almacén multi-tenant, «sin firma» significando «público» está a una mala configuración de ser un bucket abierto |

**Las cuotas sí aplican por esta puerta.** Fue un hueco declarado y está
cerrado: una credencial S3 no tiene registro de api key, así que la cuota se
resuelve desde las claves de su organización — donde el límite ya vivía, porque
`max_blob_bytes` es un tope de almacenamiento *de la organización* guardado por
clave. Se toma la más amplia, que es exactamente lo que ya hacía la puerta
nativa: una organización con una clave de 1 GB y otra de 10 GB podía guardar
10 GB usando la segunda.

Al cerrarlo salió un segundo agujero que nadie había declarado: **`UploadPart`
no tenía ningún guard**, así que subir los mismos bytes por partes se saltaba la
cuota que `PutObject` sí comprobaba. Ahora se cobra por parte, que es lo que
está en disco — `complete` solo concatena lo que un guard ya admitió.

## Qué no se ha probado

- **La suite mint de MinIO.** Prueba un servidor contra una matriz que incluye
  versionado, lifecycle y object lock, que aquí se rechazan a propósito:
  produciría una lista larga de fallos esperados y una señal verde/rojo que nadie
  leería. Se usó boto3, que es el cliente que un usuario alcanza de verdad.
- **Cargas grandes de verdad.** Las pruebas de multipart usan partes de cien
  bytes. El ensamblado es correcto por construcción, pero nadie ha subido un
  gigabyte por aquí.
- **Concurrencia.** Dos clientes escribiendo la misma clave a la vez no está
  probado. La escritura de cada objeto es atómica (fichero temporal y rename),
  así que el resultado será uno de los dos cuerpos y no una mezcla, pero cuál de
  los dos no está definido.
