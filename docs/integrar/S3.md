# API compatible con S3

> **Experimental.** Verificada contra **boto3 real** (20 comprobaciones), contra
> los vectores de prueba publicados de AWS para SigV4, y contra la **suite mint
> de MinIO**: 49 de sus 50 pruebas de `minio-py` en modo core pasan, y la que no
> es una extensión propietaria de MinIO. Más cargas de un gigabyte de verdad y
> pruebas de concurrencia — ver *Lo que las pruebas encontraron*, abajo.

Los objetos viven donde el API de blobs nativo los guarda
(`{data_dir}/blobs/{bucket}/{key}`), así que los mismos bytes se alcanzan por
cualquiera de las dos puertas, el registro de propiedad aplica a las dos, y la
cuota de una organización los cuenta una vez. Dos almacenes habrían significado
dos cuotas, dos rutas de respaldo y dos formas de quedar inconsistentes.

## Arrancarla

```toml
s3_port = 9000    # 0 (por defecto) la deja apagada
```

Puerto propio porque S3 se adueña de la raíz del espacio de rutas: `GET /` es
ListBuckets y `GET /{bucket}/{key}` es cualquier objeto. Compartiendo router con
`/v1/...`, uno taparía al otro — `/v1/health` es un bucket perfectamente válido
llamado `v1` con una clave `health`.

## Credenciales

```bash
# Como admin de una organización:
curl -X POST localhost:1234/v1/admin/s3-credentials -H "Authorization: Bearer $KEY"

# Como admin de plataforma hay que nombrar la organización:
curl -X POST localhost:1234/v1/admin/s3-credentials \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"org_id":"acme"}'
```

El secreto se devuelve **una vez** y no hay endpoint que lo vuelva a mostrar.

> **Las credenciales S3 no son las api keys, y su radio de impacto es distinto.**
> SigV4 no envía una credencial: envía una firma derivada de ella, así que el
> servidor tiene que poder **derivar la misma clave** — y para eso necesita el
> secreto en forma recuperable. Las api keys se guardan como hash SHA-256 y aquí
> serían inservibles. El secreto S3 se guarda **cifrado** con `LUMA_MASTER_KEY`,
> no hasheado: un hash no lo revierte nadie, un secreto cifrado lo lee quien
> tenga la master key. Es inherente a SigV4, no un atajo. Rótalas en consecuencia.

## Clientes

```python
import boto3
from botocore.config import Config

s3 = boto3.client(
    "s3",
    endpoint_url="http://luma:9000",
    aws_access_key_id=ACCESS_KEY,
    aws_secret_access_key=SECRET_KEY,
    region_name="us-east-1",
    config=Config(
        signature_version="s3v4",              # obligatorio, ver abajo
        s3={"addressing_style": "path"},       # no hay DNS para bucket.host
    ),
)
```

Los dos parámetros de `Config` no son opcionales:

- **`signature_version="s3v4"`.** boto3 todavía presigna con **SigV2** por
  defecto, y Luma solo soporta SigV4. Sin esto, `generate_presigned_url` produce
  una URL que se rechaza. El servidor detecta esa forma concreta y lo dice en el
  mensaje, en vez de un «se requiere una petición firmada» genérico que mandaría
  a revisar las credenciales, que están bien.
- **`addressing_style="path"`.** El estilo virtual-host mete el bucket en la
  cabecera `Host`, y sin DNS comodín eso no resuelve.

## Qué está soportado

| | |
|---|---|
| Buckets | ListBuckets, CreateBucket, **HeadBucket**, DeleteBucket (rechaza si no está vacío) |
| Objetos | PutObject, GetObject, HeadObject, DeleteObject, DeleteObjects, **CopyObject** (con `x-amz-metadata-directive` COPY y REPLACE) |
| Rangos | **`Range`** en las cuatro formas (`a-b`, `a-`, `-n`, fin más allá del objeto) con `206` y `Content-Range`; una petición insatisfacible es `416` |
| Metadatos | **`Content-Type`** y **`x-amz-meta-*`** se guardan y se devuelven por `GET` y `HEAD`, también en multipart (donde S3 los toma de la petición que inicia la subida) |
| Listado | ListObjectsV2 con `prefix`, `delimiter`, `max-keys` y continuación |
| Multipart | Create, UploadPart, Complete, Abort |
| Firma | SigV4 por cabecera y por query (presignado, con caducidad) |
| Cuerpos chunked | `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`: se desenmarca y se verifica la firma de cada chunk |
| ETag | MD5 del cuerpo para una subida simple; para multipart, MD5 de los digests de las partes más `-N`, como S3 — y **estable**: el mismo valor por completado, `HEAD` y `GET` |

## Qué **no** está soportado

Rechazado con el `NotImplemented` de S3, no ignorado en silencio: versionado,
lifecycle, ACLs, replicación, object lock, cifrado en servidor por cabecera,
tagging, configuración CORS y hosting web.

La distinción importa. Un cliente que pone una ACL y recibe un 200 **cree que el
objeto es privado** cuando no lo es; un 501 le dice la verdad.

## Divergencias conocidas

> **Los cuerpos chunked ya se desenmarcan y se verifican.** Estaba declarado
> como «se aceptan sin verificar», y eso se quedaba corto. No había *ningún*
> parser, así que el marco de chunks se guardaba **dentro del objeto**: no era un
> cuerpo sin verificar, era un objeto corrupto con un 200 de respuesta —
> `tests/e2e/s3_chunked.py` lo demuestra: quitando el parser, 600 bytes de
> payload llegan como 946. Como el marco hay que parsearlo de todas formas,
> verificar cuesta un HMAC por chunk, y la cadena —cada chunk firma la firma
> anterior— fija además su **orden**.

> **El ETag ya es MD5.** Era una divergencia declarada y está cerrada. El
> razonamiento original —no añadir una dependencia de un hash roto para un
> checksum— no se sostenía: `md-5` ya estaba en el árbol de dependencias, así que
> no costaba nada, y aquí MD5 no es una primitiva de seguridad sino un formato de
> cable. Un cliente que recalcula el ETag está buscando corrupción, y o coincide
> o la descarga parece corrupta.

| | |
|---|---|
| **Sin acceso anónimo** | S3 lo permite para buckets públicos. En un almacén multi-tenant, «sin firma» significando «público» está a una mala configuración de ser un bucket abierto |

**Las cuotas sí aplican por esta puerta.** Fue un hueco declarado y está
cerrado: una credencial S3 no tiene registro de api key, así que la cuota se
resuelve desde las claves de su organización — donde el límite ya vivía, porque
`max_blob_bytes` es un tope de almacenamiento *de la organización* guardado por
clave. Se toma la más amplia, que es exactamente lo que ya hacía la puerta
nativa: una organización con una clave de 1 GB y otra de 10 GB podía guardar
10 GB usando la segunda.

Al cerrarlo salió un segundo agujero que nadie había declarado: **`UploadPart`
no tenía ningún guard**, así que subir los mismos bytes por partes se saltaba la
cuota que `PutObject` sí comprobaba. Ahora se cobra por parte, que es lo que
está en disco — `complete` solo concatena lo que un guard ya admitió.

## Lo que las pruebas encontraron

Esta sección declaraba tres huecos —la suite mint, las cargas grandes y la
concurrencia— con el argumento de que estaban sin cubrir. Al cubrirlos aparecieron
**siete defectos reales**, seis de ellos invisibles para las 14 comprobaciones que
ya existían. Vale la pena el detalle, porque el patrón se repite: cada uno pasaba
por debajo de una prueba que miraba el sitio equivocado.

| Qué estaba roto | Cómo se veía | Quién lo encontró |
|---|---|---|
| **El router S3 no tenía límite de cuerpo propio**, así que heredaba el default de axum: **2 MiB** | La conexión se cerraba sin código de estado y sin nada en el log en cualquier `PutObject` o `UploadPart` mayor. La API no podía almacenar una fotografía | La primera parte de 8 MiB de `s3_scale.py` |
| **`Range` no se leía en absoluto** | Cada `GET` con rango devolvía **el objeto entero** con un 200. boto3 baja los objetos grandes como rangos concurrentes y escribe cada respuesta en su desplazamiento: el fichero descargado salía corrupto, sin un solo error por ningún lado | Leer un objeto grande a un desplazamiento |
| **El ETag compuesto no se persistía** | `CompleteMultipartUpload` devolvía `…-N` y todo `HEAD`/`GET` posterior devolvía el MD5 plano. `aws s3 sync`, rclone y cualquier caché que valide por ETag veían el objeto cambiar en cada comprobación | La comprobación que faltaba: la que ya existía leía el ETag **solo de la respuesta de completado** y nunca volvía a preguntar al servidor |
| **`Last-Modified` iba en ISO 8601** | No es un HTTP date. minio-py rechazaba la respuesta con «time data does not match HTTP header format». boto3 no parsea esa cabecera, así que 14 comprobaciones contra boto3 no dijeron nada | mint, en su primer `PutObject` |
| **`Content-Type` y `x-amz-meta-*` se descartaban** | Todo objeto volvía como `application/octet-stream` sin metadatos. Un JPEG subido por aquí se le sirve al navegador como descarga | mint |
| **La petición canónica se firmaba con un método literal** | `HeadBucket` no tiene ruta propia, así que axum lo servía con el handler de `GET`, que firmaba `"GET"` contra un cliente que firmó `"HEAD"`. SigV4 cubre el método: 403 indistinguible de una clave mala, en la operación que todo cliente usa para comprobar que un bucket existe | mint, en su primer test |
| **`CopyObject` no existía y no se rechazaba** | Es un `PUT` con cabecera y sin cuerpo, así que caía en la ruta de escritura normal: el destino quedaba en **0 bytes** y la respuesta era un 200. `aws s3 cp` entre dos claves destruía el destino y decía que había funcionado | mint |

El último es el que más importa de los siete: los otros seis fallan o degradan,
ese **pierde datos y responde éxito**.

### Lo que ahora está medido

- **Un gigabyte de verdad.** 1024 MiB por multipart, verificado byte a byte:
  105 MiB/s de subida y 272 de bajada en SSD NVMe. Antes las partes de las
  pruebas eran de cien bytes.
- **Concurrencia.** Ocho clientes reescribiendo la misma clave a la vez, seis
  rondas: el objeto almacenado es **siempre exactamente uno de los cuerpos**,
  nunca una mezcla. Un lector en bucle mientras un escritor la reemplaza ve solo
  versiones completas. Y seis multipart en vuelo a la vez no se contaminan entre
  sí. El razonamiento del temporal-y-rename que esta página daba por bueno
  resultó ser correcto — pero ahora está ejecutado, no argumentado.
- **La suite mint de MinIO.** 49 de 50 pruebas de `minio-py` en modo core.

### Lo único que mint sigue fallando

`test_upload_snowball_objects`, y no es S3: sube un **tar** con la cabecera
`x-minio-extract: true` esperando que el servidor lo descomprima en tres objetos.
Es una extensión propietaria de MinIO. Aquí el tar se guarda como un objeto, que
es lo que hace el S3 de Amazon.

La razón original para no correr mint —que prueba versionado, lifecycle y object
lock, que aquí se rechazan a propósito— resultó ser una preocupación menor de lo
esperado en modo `core`: esas comprobaciones viven en el modo completo.

### Lo que sigue sin probarse

- **Objetos por encima de `max_body_mb`** (100 MB por defecto). El S3 real admite
  partes de 5 GiB; aquí el cuerpo se bufferiza completo en memoria, así que el
  tope es deliberado y configurable, no un accidente. Subirlo requiere transmitir
  el cuerpo a disco, que es otro cambio.
- **`CompleteMultipartUpload` ensambla en memoria.** Un objeto de un gigabyte
  cuesta un gigabyte de RAM en ese instante. Funciona —está medido— pero no
  escala a objetos arbitrariamente grandes.
- **Los ETag que un cliente devuelve en el completado no se verifican.** S3 sí
  los comprueba y responde `InvalidPart`; aquí un cliente que mande los
  equivocados obtiene un éxito.
- **TLS en el puerto S3.** Se sirve en claro; va detrás de un proxy o de una red
  de confianza.

## Cómo reproducirlo

```bash
# Correctitud: 20 comprobaciones contra boto3
python tests/e2e/s3_client.py --admin http://127.0.0.1:1234 \
    --s3 http://127.0.0.1:9000 --api-key <clave admin>

# Cuerpos con marco de chunks, construidos a mano
python tests/e2e/s3_chunked.py --admin ... --s3 ... --api-key ...

# Tamaños reales y concurrencia (--size-mb 1024 para el gigabyte literal)
cd tests/e2e && python s3_scale.py --admin ... --s3 ... --api-key ... --size-mb 64

# La suite mint de MinIO
docker run --rm -e SERVER_ENDPOINT=host.docker.internal:9000 \
    -e ACCESS_KEY=<ak> -e SECRET_KEY=<sk> -e ENABLE_HTTPS=0 \
    -e MINT_MODE=core minio/mint:latest minio-py
```

Las tres primeras corren en CI en cada push. mint no: necesita una imagen de
más de un gigabyte y sus credenciales hay que acuñarlas antes, así que se corre
a mano y su resultado se anota aquí.
